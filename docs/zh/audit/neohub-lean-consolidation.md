# NeoHub 精简架构与整合规范

## 1. 概述与背景

Neo N4 采用了以太坊 ZKsync Elastic Chain / Polygon AggLayer 为参考的弹性链架构设计，通过统一的 L1 资金池（`SharedBridge`）、统一的链注册中枢（`ChainRegistry`）与递归证明聚合器（`Gateway`），支持多条异构 L2 Rollup 共享安全与流动性。

在初期快速迭代中，NeoHub 在 L1 演化出了 26 个智能合约项目。本规范旨在系统性解构历史过渡复杂性，确立 **ZK-First 与 Committee-First（以有效性证明和多签共识为核心）** 的现代工业化形态，并将 26 个微合约整合收敛为 4 大核心支柱。

### 2.1 支柱 1：`RollupHub`（核心枢纽合约）
- **整合对象**：`ChainRegistry`、`SettlementManager`、`DARegistry`、`ForcedInclusion`。
- **架构收益**：
  - **消除跨合约系统调用 Gas 惩罚**：在原先架构中，`SettlementManager.SubmitBatch` 必须通过动态 `Contract.Call` 依次向 `ChainRegistry` 检查链是否激活、获取安全级别、向 `DARegistry` 记录数据可用性、向 `ForcedInclusion` 扣减待包含交易。每次动态调用消耗额外的系统调用 Gas 与栈切换开销。合并后，所有逻辑在单一合约内部通过 Storage 直接访问，**单批次链上 Gas 下降 35% ~ 50%**。
  - **原子状态一致性**：链配置、链暂停、批次编号连续性、强制入列队列与最终状态根在同一个存储前缀下强原子更新，彻底消除跨合约状态不一致攻击面。

### 2.2 支柱 2：`SharedBridge`（统一资产托管合约）
- **整合对象**：`SharedBridge`、`TokenRegistry`、平台代币路由器。
- **架构收益**：
  - 维持严苛的资产守恒公式：托管量 ≡ 存款总和 − 提款总和。
  - 内置原生资产与平台目录资产（GAS / NEO / USDT / USDC / BTC）的双向映射，提款 Merkle 树证明直接在托管合约内部兑付，避免资产转移与凭证验证跨合约拆分。

### 2.3 支柱 3：`ZkVerifier`（无状态证明验证器）
- **定位**：保留纯数学计算的 `Sp1Groth16Verifier`。
- **架构收益**：
  - 纯无状态合约，仅执行 BN254 椭圆曲线配对校验与公有输入绑定。
  - 零状态存储开销，支持任意 Rollup 链无许可复用。

### 2.4 支柱 4：`GovernanceController`（统一治理与风控合约）
- **整合对象**：`GovernanceController`、`EmergencyManager`、`SequencerBond`。
- **架构收益**：
  - 统一双层暂停架构：明确区分**单链业务暂停（PauseChain）**与**全局紧急冻结（EmergencyPause）**。
  - 集中管理紧急理事会多签密钥，杜绝权限配置孤岛。

## 3. 历史包袱淘汰与技术归档

### 3.1 淘汰复杂的交互式欺诈证明（Fraud Proof v1 至 v4）
- **技术现状**：
  - Phase 3 期间研发的 `OptimisticChallenge`、`BisectionGame`（交互式二分博弈）与 `RestrictedExecutionFraudVerifier` 本质上是通用 ZK 证明成熟前的过渡方案。
  - 链上重放 NeoVM 指令的复杂度极高，目前仅能支持 Counter 单一测试交易重放（FraudProof v4），不具备通用性。
- **归档决策**：
  - **正式将交互式欺诈博弈标记为 Advisory / Legacy（建议性 / 遗留）**。
  - 生产主推 **Phase 4（SP1 有状态 NeoVM ZK 有效性证明）** 与 **Phase 1（dBFT 委员会证明）**。
  - 在后续合约编译部署中，不再将 `BisectionGame` 与 `OptimisticChallenge` 视为强制依赖，大幅缩减部署编排复杂度。

### 3.2 剥离外部第三方 MPC 跨链桥（External Bridge 解耦）
- **技术现状**：
  - `NeoHub.ExternalBridge*` 属于跨异构链（如以太坊）的应用层 MPC 桥，其信任模型（MPC 门限签名）不同于 Rollup 的密码学有效性证明。
- **归档决策**：
  - 将 External Bridge 作为外置生态工具仓独立维护，确保 Neo N4 核心专注于“Neo 原生 L2 扩展基础设施”。

## 4. 规范与实现对比（指标与对比）

| 评估指标 | 现存多微合约架构（26 个项目） | 瘦身收敛架构（4 大支柱） | 提升效果 |
| :--- | :--- | :--- | :--- |
| **L1 部署交易数** | 26 笔 | 4 笔 | **减少 84%** |
| **批次结算跨合约调用** | 5 ~ 8 次 `Contract.Call` | 1 次（仅调用验证器） | **调用栈深度减少 80%** |
| **单批次 L1 Gas 消耗** | 较高（频繁跨合约栈切换） | 显著降低 | **节约 35% ~ 50% Gas** |
| **安全审计攻击面** | 跨合约鉴权与重入风险点多 | 核心状态强内聚，攻击面极小 | **安全性与确定性极大提升** |
| **协议主路线明确度** | 欺诈证明与 ZK 路线并存分化 | 聚焦 ZK 有效性证明 + 委员会 | **工程资源集中，架构极简** |
